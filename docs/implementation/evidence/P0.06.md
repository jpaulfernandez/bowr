# P0.06 — Manage account access and delete your own data

**Slice ID and outcome:** P0.06. A member saves their settings, then deletes their account after confirming with a fresh sign-in. The page tells them deletion is still in progress until every stored object is confirmed gone and the sign-in has been removed. An owner can suspend and restore members. An owner with active members must transfer ownership, again after a fresh sign-in, before deleting their own account. All acceptance cases pass locally. **Withheld:** the fresh-authentication path through Google OAuth. It uses the same challenge but needs the staging OAuth client (P0.01 withheld gate). Analytics identity reset is wired as an account disposer seam; the PostHog adapter itself arrives in P0.07-T4.

## Environment, fixtures and clock

- Local stack with versitygw storage, the local worker and Inbucket. The same run uses the AUTH and MEDIA fixtures. Fresh sessions are real magic-link sign-ins through GoTrue.
- Fresh authentication uses the verified JWT's `session_id` and its `amr` authentication timestamp. A refreshed token keeps its original `amr` time and session, so it cannot satisfy a challenge created after that sign-in.
- The quarantine recheck from P0.03 is time-based: `not_before` is when the upload capability expires, plus 1 minute. Tests that need the deletion to finish move `not_before` to now, instead of waiting about 10 minutes.

### What each case proves

- **A1 (suspension blocks new access immediately):**
  - As soon as the owner suspends a member, RLS reads of that member's own profile return nothing.
  - `/media/access` returns 403, and bootstrap reports `suspended`.
  - A link signed before the suspension still works until it expires (at most 300 s). The confirmation dialog says so: signed links "cannot be recalled".
  - Suspending the owner returns `CANNOT_SUSPEND_OWNER`, and a nonowner gets 404.
  - Restoring the member brings access back.
- **A1 (owner sees aggregates only):** The admin overview contains no asset, upload, object key, email, city or timezone. A profile patch that tries to set `role` fails `VALIDATION_FAILED`.
- **A2 (only a new sign-in proves fresh authentication):**
  - These cannot verify a challenge: the requesting session, the same session with a refreshed token, and a sign-in that happened before the challenge was created.
  - A new sign-in after the challenge verifies it once, and a second verify returns 403.
  - The proof is refused for the wrong user, the wrong action, after expiry, and when guessed. None of these delete anything.
- **A2 (concurrent ownership transfer):** Two concurrent transfers with two valid proofs give 200 and 404 (404 because the actor is no longer the owner). The result is exactly one owner and one audit event.
- **A3 (owner deletion rules):**
  - The sole owner with active friends gets `OWNER_TRANSFER_REQUIRED`, and the proof stays unusable.
  - With no other active members, the owner deletes; the friend's Auth user survives.
  - The installation then needs `private.bootstrap_owner`, which succeeds for the friend.
  - Invite and audit relationships to the deleted user are `on delete set null`.
- **A4 (storage fails halfway):**
  - With the storage gateway stopped, deletion starts (202) and every session of the account loses access. Domain rows are gone, the Auth user stays, and the status reads `objects_pending` with objects remaining.
  - The status body has exactly `state`, `started_at`, `completed_at` and `objects_remaining`, and contains no name, email, user ID, object key or upload.
  - A worker holding a claim from before the deletion cannot attach its result.
  - After storage returns, a retry deletes every object from the preserved manifest, confirms each is absent, then deletes the Auth user. The status reads `complete` with 0 remaining.
  - An unknown status token gets 404.
- **Demo (E2E):**
  - The member uploads a photo, asks for deletion, and a confirmation link is emailed. The membership stays active until the link is opened.
  - The fresh tab shows "Delete your account" and passes axe.
  - After the permanent deletion, `/account-deleted` first shows "Deleting your account" and passes axe. Once objects and Auth are confirmed removed, it shows "Account deleted".
  - The original tab's session no longer works.
  - The owner flow suspends a member and transfers ownership through the same fresh-sign-in confirmation.

## Database, object and ledger evidence

- The deletion order is `svc_start_account_deletion`, in one transaction:
  1. Mark the membership `deleting`.
  2. Cancel open jobs.
  3. Delete `auth.sessions`.
  4. Queue every live `media_objects` row as an `account_deleted` deletion task.
  5. Call `private.scrub_account_domain`.
  6. Record `private.account_deletions`, which holds no identity or content beyond the user ID needed for the manifest.

  The Auth user is deleted only when no pending deletion task remains for the user. `svc_account_deletions_ready` claims those rows with `for update skip locked` and a short `claimed_until`, so overlapping cron and manual runs do not race.
- `ai_usage.user_id` is detached (set to null), so the shared ledger keeps its totals.
- Found during this slice:
  - Two maintenance runs could race to delete the same Auth user. The claim column fixed it.
  - A stored photo keeps a deletion `objects_pending` until its quarantine recheck runs after the upload capability expires. This follows ARCHITECTURE §12.2. The UI reports "Deleting your account" until then and never claims deletion early.

## Accessibility, recovery and zero-AI checks

- Settings, the confirmation page and the deletion status pass axe (WCAG 2.2 AA tags).
- Every destructive action uses a dialog that lists its consequences. No flow depends on camera, swipe or drag.
- Account deletion needs no AI.
- Client-side account resources are released through `onAccountDispose` and `disposeAccountResources` in `apps/app/src/lib/account-lifecycle.ts`, and the TanStack cache is cleared on sign-out or account change. This is the extension point where P0.07-T4 resets analytics identity.
- `private.scrub_account_domain` is the database extension point where later phases add their domain cleanup.

## Deployment flag and rollback

The migration is additive. Rolling back the Edge or app artifacts leaves any deletions already started in `private.account_deletions` and `private.deletion_tasks`, and the cron completes them. Never drop these tables or the manifest during a rollback.
