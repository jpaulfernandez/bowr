# P0.07 — Operate and restore the private foundation

**Slice ID and outcome:** P0.07. Locally, an operator can:

- Detect a stopped cleanup scheduler through a health check that does not depend on that scheduler.
- Recover it with one command. Queued deletions drain, and the deletion status never says "deleted" early.
- Restore an encrypted export into an isolated database without reviving an account deleted after the export, without resuming old sessions or jobs, and without re-sending old paid AI work.

Analytics are allowlisted, redacted and tied to sign-out.

**Withheld (staging gates):**

- P0.07-A1 on staging: the external monitor on a deployed project.
- P0.07-A2 on staging: a restore of a staging export, with sign-in re-established on a hosted project.
- P0.07-A4: deployed deep links and callbacks, and an artifact rollback.
- Daily exports on a schedule, provider resource alerts, and PostHog project settings.

No staging environment exists yet.

### What each case proves

- **A1 (missed heartbeat and recovery):**
  - With the schedules stopped and the `temporary_cleanup` and `account_deletion` heartbeats an hour old, `GET /maintenance/health` returns 503. It names both tasks and counts the account being deleted.
  - The body contains no email, object key or upload path. The maintenance secret and a missing token both get 404.
  - The member's deletion status still reads `objects_pending`.
  - `pnpm ops:recover-maintenance` re-enables every paused schedule and runs the tasks. Afterwards `stale_tasks` is empty, the deletion status is `complete` with 0 objects, and the Auth user is gone.
  - A failed run records `last_error` without refreshing the heartbeat. pgTAP covers the stale threshold (two intervals plus 2 minutes), degraded status, and recovery by a successful run.
- **T2 (cleanup targets):**
  - An upload whose signed PUT expired without completion is cancelled, its asset reaches `deleted`, and its bytes are gone from storage. The deletion task finished before its deadline, which is exactly 3,600 s after the object became deletable.
  - A late completion then gets `UPLOAD_CANCELED`.
  - Account deletion tasks get a 24-hour deadline, and an overdue task is counted as `deletions_overdue`.
  - Expiry is checked at signing: renewing a slot whose temporary asset expired returns `UPLOAD_NOT_RENEWABLE`, and a media read for it returns no URL. The callback check is the `UPLOAD_CANCELED` case above.
  - Orphan reconciliation queues an unregistered object and deletes it. It leaves registered keys alone and counts a registered original missing from storage. The scheduled task lists the real bucket through ListObjectsV2.
- **T3 (journal):** Starting an account deletion writes the journal row in the same transaction (pgTAP). The `account_deletion` task writes `deletions/<date>/<id>.json` to the journal bucket with exactly `kind`, `subject_id` and `recorded_at`, and marks it exported before removing the identity.
- **A2 (local rehearsal):**
  - Setup: an export is taken while one member has a stored photo, the other has an upload waiting for processing, and an AI attempt is reserved.
  - After the export, the first member deletes their account completely.
  - The restore goes into a fresh isolated database. After replaying the journal:
    - The deleted member is `deleting`, with a scrubbed profile, no assets and an open deletion.
    - The other member is intact.
    - `auth.sessions` and `auth.refresh_tokens` are empty.
    - No job is queued, running or retrying. The waiting upload shows `failed`/`RESTORED`, which the member can retry.
    - The reserved AI attempt is `unknown` (counted, never resent), and AI is paused with the reason `restore`.
  - The report shows an export age of seconds (RPO met), a restore time of seconds (RTO met), at least 2 sessions revoked, and at least 1 deletion replayed. It contains no names, emails or keys.
  - The script refuses a non-empty target and refuses the live `DATABASE_URL`.
- **A3 (analytics):**
  - Every captured client event has exactly `api_key`, `event`, `distinct_id`, `timestamp` and `properties`. The event name is in the allowlist, and its property keys are exactly the allowlisted ones.
  - The payloads contain no `@`, URL, file name, display name, `?` or upload ID. Routes are templates such as `/wardrobe/gather`.
  - While signed in, `distinct_id` is the internal user ID. After sign-out, events carry a new `anon-…` ID.
  - With the analytics host refusing connections, an upload still reaches Ready and settings still save.
  - Server side:
    - One budget-mode transition sends one `budget_mode_changed` event, with only `{ mode, $process_person_profile: false }` and `distinct_id: bowr-system`. A second run sends nothing.
    - With PostHog down, `ai_rollover` still returns 200 (`analytics_failed: 1`) and the event waits in the outbox.
    - A later transition in the same month is a new event.
  - The contract tests reject free-text codes, raw paths, invite codes and extra fields.
- **Owner summary:** Admin → Background work lists six scheduled tasks with times, and deletion, job and AI counts. It passes axe, and a member gets 404 from the operations endpoint.

## Database, object and ledger evidence

- Found during this slice:
  - Abandoned slots (created, maybe uploaded, never completed or cancelled) had no deletion path at all. Their bytes would have stayed in quarantine indefinitely. `svc_temporary_cleanup` now expires them.
  - Renewal could extend a slot past its temporary asset's deadline. It is now bounded.
  - The first outbox dedupe key (`period:from:to`) suppressed a repeated transition in the same month. A per-period transition counter replaced it.
- Unrelated keys found in the local bucket from earlier test runs are younger than the 6-hour grace period, so the daily task leaves them alone. The grace period protects worker output written before its completion callback.

## Deployment flag and rollback

- The migration is additive. `bowr-media-deletion` is replaced by `bowr-temporary-cleanup`, which also deletes due objects. Rolling back the Edge code would leave `temporary_cleanup` unknown to the old function (404), so roll back the schedule with the code:

  ```sql
  select cron.unschedule('bowr-temporary-cleanup');
  select cron.schedule('bowr-media-deletion', ...);
  ```

- Analytics is off when `EXPO_PUBLIC_POSTHOG_*` and `POSTHOG_*` are unset.
- Account deletion fails closed without `DELETION_JOURNAL_BUCKET`: Auth removal waits and `journal_unexported` is reported.
