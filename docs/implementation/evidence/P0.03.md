# P0.03 — Upload and retrieve a private validated photo

**Slice ID and outcome:** P0.03. From a minimal Gather upload receipt, A uploads fixtures and views the sanitized original. B, pending and suspended identities cannot obtain new authorized access to it. Local acceptance passes with a local S3-compatible gateway in place of R2 and the worker running as a local process. **Staging gates are withheld:** the private R2 bucket and its CORS (P0.03-T2), and the Modal deployment and HEIC proof on Modal (the staging part of P0.03-A1).

## Environment, fixtures and clock

- Local Supabase stack, `pnpm storage:start` (gateway with private bucket and CORS for the two local origins), and `pnpm worker:serve`, which accepts wake-ups with `Modal-Key`/`Modal-Secret` headers exactly as Modal proxy auth would.
- MEDIA fixture: synthetic images generated by `services/worker/tests/conftest.py`. They cover JPEG with EXIF orientation 6, a camera make and GPS; PNG, WebP and HEIC; an embedded sRGB profile; CMYK JPEG; transparency; animated WebP and APNG; GIF, TIFF, SVG, HTML and empty bytes; truncated JPEG; and the 40 MP boundary (8000×5000 accepted, 8001×5000 rejected). The 20 MiB limit is tested at the byte boundary and with a 20 MiB + 1 upload. No real photos are committed.
- Clock control: deletion tasks are made due by SQL (`not_before = now()`). A temporary asset's expiry is set three seconds ahead to prove that signed URLs are clipped to it.

### What each case proves

- **A1:** JPEG, PNG, WebP, HEIC and HEIF become WebP with no `EXIF`, `XMP ` or `ICCP` chunks. EXIF orientation 6 yields a 200×400 output with the red half on top, and the camera make string is absent. The longest edge is at most 1024 px, or 2048 px for the care-label path. Small images are not upscaled. The following are rejected with stable codes and no published asset: PNG declared as JPEG and JPEG declared as HEIC (`MEDIA_TYPE_MISMATCH`); HTML, SVG, GIF, TIFF and empty files (`UNSUPPORTED_MEDIA`, and the decoders for these never run); animated WebP and APNG (`ANIMATED_IMAGE`); truncated JPEG (`CORRUPT_IMAGE`); over 40 MP (`TOO_MANY_PIXELS`, checked from the header before decoding); over 20 MiB (`FILE_TOO_LARGE`, both declared and stored size). Through the real path, the served bytes match the asset's SHA-256 and carry `Cache-Control: private, no-store`.
- **A2:** Replaying a still-valid PUT after normalization rewrites only the quarantine key; the viewed bytes keep the published SHA-256. The recheck task, due after the upload URL expires, deletes the recreated object and confirms its absence. After a cancel, completion returns `UPLOAD_CANCELED` and access returns `not_found`. The object is deleted, and a replay recreates it; the recheck, scheduled after `upload_expires_at`, removes it again and marks the asset `deleted`.
- **A3:** For A's asset, B gets `not_found` from media access and 404 from complete, renew and cancel. Pending and suspended identities get 403. Only the `original` variant of a ready asset can be signed; `cutout`, `thumbnail`, `quarantine`, `../original` and empty variants return `not_found`. Responses have no `object_key` or bucket fields, and a client-supplied `object_key` is refused (422). A signed URL is clipped to a temporary asset's expiry (the request is refused after it passes), and a new request requires fresh authorization: an expired asset returns `not_found`, and a suspended member gets 403. RLS gives B zero rows of A's media, and keys, jobs and deletion tasks are not granted to clients.
- **A4:** A repeated completion with the same key returns an identical body and one job; a different entry under that key returns `IDEMPOTENCY_CONFLICT`. Batch creation behaves the same way. After an HTTP PUT alone the entry stays `awaiting_upload` and is not signable. Completion reports `uploaded` and a job ID, not ready, and completion without the object returns `UPLOAD_MISSING`. In the E2E journey, the receipt shows "Uploaded · checking photo" until the worker publishes, shows the per-file failure next to the good photo, and survives reload.
- **T3 (worker API):** A claim token works once, and wrong tokens are refused. User JWTs, capabilities for another job, and tampered capabilities are refused on completion. A fabricated output whose checksum does not match the stored object is not published. A result for an entry canceled mid-run is fenced (`stale`), is never attached, and its output is queued for deletion.
- **T4 (UI):** The Gather screen shows server-supplied limits, pre-checks unsupported and oversized selections, and offers "Take a photo" with a file-chooser fallback. The receipt uses a polite live summary line and has per-file retry and cancel. A 403 on the first image load triggers exactly one new authorization and the image then loads. Gather and receipt pass axe and reflow at 320 px.

## Database, object and ledger evidence

- Quarantine keys follow `uploads/{user}/{entry}/{128-bit nonce}` and validated keys follow `users/{user}/assets/{asset}/{media_revision}/original-g{lease}.webp`. Both are chosen by the server; the worker receives only exact signed URLs.
- Object absence is asserted with HEAD 404 against the gateway after each deletion task, and tasks move to `done` only after that confirmation.
- The worker suppresses `httpx` request logging, because a pytest case showed that it would otherwise log signed URLs at INFO level.

## Accessibility, recovery and zero-AI checks

- Covered under T4 above. A visual review at 390 px found two utilities using spacing steps outside the token scale (the skip link was always visible, and a placeholder had zero size). Both are fixed, and `pnpm lint` now fails on such classes (`apps/app/scripts/check-classnames.mjs`).
- Recovery: per-file failure copy, retry and cancel, and a single refresh of an expired image before "Image unavailable".
- No AI is used. Validation is independent of Gemini, as P0.05-A1 requires.

## Deployment flag and rollback

Nothing is deployed. HEIC is advertised only when `UPLOAD_HEIC_ENABLED=true`, which defaults to off in the staging runbook until the Modal HEIC fixture passes. The migration is additive.
