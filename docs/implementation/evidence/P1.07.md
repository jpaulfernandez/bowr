## Verification history

- **Label vs. vision order (P1.03 fix):** the P1.03 label case failed once in the full regression. The piece kept the vision guess "cotton" instead of the printed "100% cotton".
  - **Cause:** a label result carries the field versions from when its job was claimed. When the tags stage finished first, the guess bumped the material's version, and the printed value was then dropped as stale. So which one won depended on completion order, against the rule that a visual guess never replaces a label fact.
  - **Fix:** `private.apply_suggestion` now lets a label replace a field whose current value came from vision even at a newer version. Locked values and member edits (edits always lock) are still never replaced.
  - **Proof:** three pgTAP cases where vision lands first. Two failed before the migration and all three pass after it.
- **Fresh-authentication timing (P0.06 test):** the P0.06 ownership-transfer E2E failed intermittently (1 of 3 runs alone) with "confirmation expired or already used".
  - **Cause:** the sign-in time comes from the access token in whole seconds. A sign-in in the challenge's own second cannot be told from one just before it, so it is refused. That is P0.06's deliberate, tested behavior. The harness opened the emailed link within the same second, which no person can do.
  - **Tried and reverted:** truncating the challenge time to the second. It broke the P0.06 integration case "a sign-in that happened before the challenge cannot verify it" and weakened the check, so it was reverted.
  - **Resolution:** the E2E now waits for the next whole second before opening the link. Two pgTAP cases pin the behavior: the same second is refused, the next second verifies.
  - All three P0.06 E2E cases then passed 5 repeats each (15 of 15), and the full suite passed.
  - **Product note:** a member who opens the link within a second of requesting it sees "expired" and must start again. This is recorded, not changed.
- **Cleanup batch assumption (P0.07 test):** two P0.07 cases failed in full runs but passed alone. In one, an expired upload's object was still `deletion_pending`; in the other, the orphan was still present.
  - **Cause:** each deletion run claims at most 100 due objects, oldest first. The failing runs deleted exactly 100. Earlier suites now leave a larger backlog, so the test's object waited for the next run.
  - The product behaves as designed: runs repeat on schedule, and each task has a one-hour deadline.
  - **Fix:** the tests now repeat the run (at most 10 times) until their object is gone, and still assert the task finished before its deadline.
  - **Proof:** the full integration suite then passed (128) with the backlog present.
- **Environment interruption:** the container restarted mid-slice, taking Docker, the worker and the fake provider down. The stack was restarted with the README commands before the final runs.
